# Modexa — закрытое тестирование

Этот документ — критерии допуска к закрытому тестированию. Не считать пункт выполненным только потому, что код уже находится в `main`: каждый пункт должен пройти проверку в локальном окружении и на тестовом Discord-сервере/Telegram-группе.

## 1. Перед запуском

- [ ] Node.js и pnpm установлены; зависимости поставлены через `pnpm install`.
- [ ] В `.env` задан `MODEXA_API_KEY` — случайный секрет не короче 32 символов.
- [ ] Настроены `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, точный `DISCORD_REDIRECT_URI`.
- [ ] В Discord Developer Portal redirect URI совпадает с `DISCORD_REDIRECT_URI`.
- [ ] Настроены токены тех адаптеров, которые будут тестироваться: `DISCORD_BOT_TOKEN` и/или `TELEGRAM_BOT_TOKEN`.
- [ ] `MODEXA_DATABASE_PATH` указывает на постоянный путь; API и Runner используют один и тот же файл SQLite.
- [ ] В production HTTPS завершается на reverse proxy; внешние origins перечислены в `MODEXA_ALLOWED_ORIGINS`, если Dashboard/API разнесены по origin.
- [ ] Секреты не закоммичены, тестирование проводится на отдельных серверах/группах, а не на основном сообществе.

## 2. Автоматическая проверка

Из корня репозитория выполнить:

```powershell
pnpm install
pnpm verify
```

Допуск: обе команды завершились с кодом 0. Если `pnpm verify` падает — исправить причину и повторить полную проверку до начала ручного тестирования.

## 3. Проверка доступа

- [ ] Без авторизации API закрывает защищённые маршруты.
- [ ] Discord OAuth позволяет менеджеру управлять только Discord-сообществами, где у него есть права.
- [ ] Обычный OAuth-сеанс не получает доступ к `/api/system`, `/api/runtime`, `/api/runtime/logs` и `/api/backup`.
- [ ] Владелец с корректным API-ключом может открыть OWNER FUNCTIONS.
- [ ] Пользователь без API-ключа может пользоваться обычной частью Dashboard; отсутствие доступа к OWNER FUNCTIONS не должно ломать обзор.
- [ ] Пользователь без прав не может менять настройки чужого сообщества или состояние команд.
- [ ] Повторный вход/выход и истечение OAuth-сеанса обрабатываются без зависания Dashboard.

## 4. Ручной smoke test

- [ ] Запустить `pnpm dev`; убедиться, что Runner стартует и ожидаемые адаптеры не завершаются с ошибкой.
- [ ] Открыть Dashboard в чистой сессии браузера, войти через Discord и обновить страницу.
- [ ] Проверить список Discord-серверов: установленные и доступные для приглашения отображаются отдельно; недоступные серверы не предлагают управление.
- [ ] Пригласить бота на отдельный тестовый сервер и проверить повторное появление сервера в Dashboard.
- [ ] Изменить настройку сообщества и состояние команды, перезапустить приложение и проверить сохранение.
- [ ] Проверить основные команды `/ping`, `/help`, `/menu`, `/account`, `/settings`; проверить, что community-only команды не выполняются из DM.
- [ ] Проверить модерацию только на тестовых аккаунтах и с корректными правами.
- [ ] В Telegram-группе администратор и бот имеют права администратора; выполнить `/dashboard_link`, ввести выданный 16-символьный код в Dashboard и убедиться, что повторное использование/просроченный код отклоняются.
- [ ] Проверить, что Telegram-группа появляется как identity выбранного Modexa-сообщества и как Bridge endpoint.
- [ ] Если тестируется Bridge: проверить оба направления Telegram ↔ Discord, защиту от петли, работу при удалённом endpoint и отсутствие «висячих» связей.
- [ ] Проверить мобильную ширину Dashboard и короткое окно браузера: меню прокручивается, основные действия доступны.
- [ ] Проверить резервную копию и возможность восстановить её на копии базы, а не поверх единственной рабочей базы.

## 5. Критерии остановки

Закрытое тестирование не начинать, если обнаружено хотя бы одно:
- пользователь может менять данные другого сообщества;
- OAuth без API-ключа открывает OWNER FUNCTIONS;
- Runner падает или теряет данные после перезапуска;
- ошибки Bridge создают повторяющиеся сообщения или отправляют их не в те чаты;
- `pnpm verify` не проходит;
- нет свежей резервной копии перед тестом с реальными данными.

## 6. Сбор обратной связи

Для каждого дефекта записывать: шаги воспроизведения, ожидаемый результат, фактический результат, время, платформу, ID тестового сообщества/чата и относящиеся к ошибке логи. Не прикладывать токены, API-ключи, cookies или персональные данные участников.


## 7. Dashboard-сессии и Docker (обязательно перед допуском)

- [ ] Войти через Discord OAuth, перезагрузить страницу и убедиться, что пользователь остаётся авторизован.
- [ ] Проверить продление Discord access token: после истечения access token API должен обновить его через refresh token или корректно попросить войти повторно.
- [ ] Перезапустить контейнер и проверить, что незавершившаяся OAuth-сессия восстанавливается из SQLite; при смене `MODEXA_API_KEY` старые зашифрованные сессии должны безопасно сбрасываться.
- [ ] Войти в OWNER FUNCTIONS, обновить Dashboard и убедиться, что авторизация сохраняется через HttpOnly cookie; проверить, что `modexa_api_key` отсутствует в localStorage.
- [ ] Проверить, что в production cookie имеют атрибуты `HttpOnly`, `SameSite=Lax` и `Secure` при HTTPS.
- [ ] Выполнить `docker-compose config` и `docker-compose build` на сервере до остановки или пересоздания существующего контейнера.
- [ ] Проверить `docker-compose up -d`, `docker-compose ps`, `docker-compose logs --tail=200 modexa` и `curl -fsS http://127.0.0.1:3000/health`.
- [ ] Убедиться, что приложение доступно только на loopback-порту `127.0.0.1:3000`, а публичный доступ проходит через HTTPS reverse proxy.
- [ ] Выполнить штатный `docker-compose stop modexa` и проверить, что Runner завершился, SQLite не повреждена, а повторный запуск восстанавливает данные.
- [ ] Проверить, что данные остаются в `/opt/modexa/data` на хосте, а не только внутри контейнера.
- [ ] Перед обновлением сохранить копию SQLite и `.env` вне репозитория с ограниченными правами доступа; не включать `.env` в backup, публикуемый тестировщикам.

## 7. Авторизация и разделение ролей

- [ ] Вход владельца через API-ключ выдаёт отдельную непрозрачную HttpOnly-сессию; значение API-ключа не хранится в cookie.
- [ ] Сессия владельца переживает перезапуск API и удаляется при выходе; смена MODEXA_API_KEY инвалидирует старые сессии.
- [ ] Вход через Discord работает при возврате через localhost/настроенный MODEXA_DASHBOARD_URL; handoff одноразовый, после обмена URL очищается.
- [ ] Пользователь Discord после перезагрузки Dashboard остаётся авторизованным; при истечении сессии UI сбрасывает состояние и предлагает повторный вход.
- [ ] Пользователь с Discord-доступом видит только локальные сообщества, связанные с Discord-серверами, которыми он управляет.
- [ ] Пользователь не может читать аналитику/автоматизации всех сообществ без указания доступного communityId.
- [ ] Менеджер Discord-сервера может изменять только данные своего сообщества; проверить роли, рейтинг, приветствия, AutoMod, команды, автоматизации и модерацию.
- [ ] Обычная Discord-сессия не имеет доступа к /api/system, /api/runtime, /api/runtime/logs, /api/backup и OWNER API-функциям.
- [ ] Подмена communityId, automationId или ID пользовательской команды на чужой объект возвращает отказ и не изменяет данные.
- [ ] Выход очищает cookie; повторный запрос с удалённой/истёкшей cookie не даёт доступ.

## 8. Регрессия Dashboard

- [ ] Владелец: вход → обновление страницы → навигация → выход.
- [ ] Discord-пользователь: вход → обновление страницы → выбор сервера → переход по страницам → выход.
- [ ] Несколько параллельных запросов не переводят Dashboard в состояние выхода при обычном ответе 403.
- [ ] Ошибка одной страницы не ломает остальные страницы Dashboard.
- [ ] На узком экране меню, таблицы, формы и диалоги остаются доступны.
- [ ] Все значения от API, вставляемые в innerHTML, проходят HTML-экранирование.
