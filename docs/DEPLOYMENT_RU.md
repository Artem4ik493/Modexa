# Modexa — инструкция по развёртыванию (Россия + Германия)

**Цель:** запустить Modexa в отдельном Docker-контейнере на немецком сервере, а весь публичный доступ к API и Dashboard направлять через российский сервер с aaPanel/Nginx.

- Репозиторий: https://github.com/Artem4ik493/Modexa
- Ветка: `main`
- Публичный домен: `api.artem4ik493.ru`
- Локальная разработка: `C:\\dev\\modexa-platform`

> Это инструкция, а не подтверждение выполненного развёртывания. Перед выполнением команд сверяйся с актуальными файлами проекта и реальным состоянием серверов. Сборка и тесты не считаются пройденными, пока их фактически не запустили.

## 1. Архитектура

```text
Пользователи
    │ HTTPS
    ▼
api.artem4ik493.ru → Российский сервер (aaPanel + Nginx)
    │
    │ защищённый upstream: VPN-туннель или TLS
    ▼
Немецкий сервер: отдельный Docker Compose-проект Modexa
    ├── API
    ├── Dashboard
    ├── Runner
    ├── Telegram-бот
    ├── Discord-бот
    └── SQLite в постоянном каталоге

Отдельно, без изменений:
    ├── marzban-marzban-1
    └── marzban-node-marzban-node-1
```

**Правила архитектуры:**

1. Всё, что относится к приложению Modexa, включая обоих ботов, API, Dashboard и Runner, работает в Германии.
2. Modexa запускается отдельно от Marzban и не должен менять его Compose-конфигурацию, порты, сетевой режим или VPN-маршруты.
3. Российский сервер — публичная точка входа: DNS, TLS и Nginx reverse proxy.
4. DNS-запись `api.artem4ik493.ru` указывает на публичный IP российского сервера, не немецкой ноды.
5. Данные SQLite должны сохраняться вне файловой системы контейнера.
6. Не переключай ботов между polling и webhook без проверки актуального кода.

## 2. Что уже известно о немецком сервере

По полученным ранее выводам:

- ОС Ubuntu 22.04, Docker установлен.
- Контейнеры Marzban: `marzban-marzban-1` и `marzban-node-marzban-node-1`.
- Оба контейнера используют host network.
- Docker-сети `bridge`, `host`, `none` существуют.
- На момент проверки TCP-порт 3000 не отображался как занятый.
- Установлены `iptables-persistent` и `netfilter-persistent`.
- Присутствуют VPN-интерфейсы/правила `wg0` и `wg-cascade`.

Перед развёртыванием повтори на немецком сервере:

```bash
ss -lntp | grep -E ':(3000|3001)\\b' || true
docker ps --format 'table {{.Names}}\\t{{.Ports}}'
docker network ls
```

Не выполняй `iptables -F`, не очищай Docker-цепочки и не заменяй целиком firewall. Обычные правила INPUT могут не ограничивать опубликованные Docker-порты: трафик может проходить через FORWARD/DOCKER-USER.

## 3. DNS и домен

В DNS-панели настрой запись:

| Тип | Имя | Значение |
|---|---|---|
| A | `api` | Публичный IPv4 российского сервера |

Добавляй AAAA только если IPv6 российского сервера действительно настроен и доступен.

Проверка:

```bash
nslookup api.artem4ik493.ru
```

Адрес должен соответствовать российскому серверу.

## 4. Размещение Modexa в Германии

### 4.1. Получить проект

Используй отдельный каталог, например `/opt/modexa`. Для приватного репозитория предварительно настрой безопасный Git-доступ.

```bash
mkdir -p /opt
cd /opt
git clone https://github.com/Artem4ik493/Modexa.git modexa
cd /opt/modexa
git checkout main
```

Если каталог уже существует, не клонируй поверх него. Проверь локальные изменения и обновляй существующий checkout:

```bash
git status
git pull --ff-only
```

Не вставляй токены GitHub в команды, публичные сообщения или эту инструкцию.

### 4.2. Проверить актуальные файлы

```bash
cd /opt/modexa
ls -la
sed -n '1,240p' docker-compose.yml
sed -n '1,240p' .env.example
```

Сверь конфигурацию с актуальным `docker-compose.yml`, `Dockerfile`, `.env.example` и README. Если структура отличается от примеров, руководствуйся актуальными файлами репозитория.

### 4.3. Переменные окружения

Создай локальный серверный файл:

```bash
cd /opt/modexa
cp .env.example .env
nano .env
chmod 600 .env
```

Заполни все обязательные переменные по текущему шаблону и коду. Проверь как минимум:

- токен Telegram-бота;
- токен Discord-бота и OAuth client ID/secret, если они требуются;
- `DISCORD_REDIRECT_URI=https://api.artem4ik493.ru/auth/discord/callback`;
- `MODEXA_DASHBOARD_URL=https://api.artem4ik493.ru/`;
- `MODEXA_DATABASE_PATH=/app/data/modexa.sqlite`, если этот путь поддерживается текущим кодом;
- `HOST=0.0.0.0` и `PORT=3000`, если приложение использует эти переменные.

Это примеры значений, которые нужно сверить с текущим `.env.example`; не добавляй неподдерживаемые переменные наугад. Не оставляй секреты-заглушки. Убедись, что `.env` исключён из Git и не публикуй его содержимое.

Прокси для исходящих запросов ботов — отдельная настройка. Не путай её с reverse proxy, который принимает входящие запросы пользователей на российском сервере.

### 4.4. Постоянная база

Если Compose монтирует `./data:/app/data`, создай каталог:

```bash
mkdir -p /opt/modexa/data
```

Убедись, что путь соответствует текущему Compose-файлу. Не удаляй каталог базы при обновлениях. Перед миграциями SQLite создавай резервную копию с гарантией целостности.

### 4.5. Сборка и запуск

Убедись, что команды выполняются из каталога Modexa, а Compose-проект отделён от Marzban. Не запускай `docker compose down` из каталога Marzban.

```bash
cd /opt/modexa
docker compose config
docker compose build
docker compose up -d
docker ps --format 'table {{.Names}}\\t{{.Status}}\\t{{.Ports}}'
docker logs --tail=200 <имя-контейнера-modexa>
```

Если доступна только старая команда `docker-compose`, используй её после проверки версии. Имя контейнера возьми из фактического вывода `docker ps`; не вводи placeholder буквально.

Проверь логи, healthcheck и endpoint здоровья, если он реализован. Статус `Up` сам по себе не подтверждает, что приложение работает корректно.

## 5. Защита канала между серверами

Предпочтительно передавать upstream через уже настроенный WireGuard-туннель, если он действительно обеспечивает связность между российским и немецким серверами. Наличие интерфейсов `wg0`/ `wg-cascade` на Германии само по себе этого не доказывает.

- API не должен быть доступен всему интернету.
- Разреши соединение с портом Modexa только от российского сервера или через конкретный защищённый интерфейс.
- Если VPN-туннеля нет, настрой защищённый транспорт или TLS на upstream.
- Не передавай сессии и другие чувствительные данные по незашифрованному HTTP через публичный интернет.

Перед изменением firewall:

1. Сохрани текущие правила и выясни, как они восстанавливаются после перезагрузки.
2. Убедись, что SSH и VPN-доступ останутся доступными.
3. Не очищай существующие цепочки и не изменяй правила Marzban.
4. Добавляй узкие правила только после определения реального IP/интерфейса российского сервера.
5. Проверь доступ через reverse proxy и недоступность API напрямую из посторонней сети.
6. Сохраняй изменения в постоянные правила только после проверки.

IP российского сервера здесь не зафиксирован. Получи его фактическим запросом на российском сервере: `curl -4 https://api.ipify.org`.

## 6. Reverse proxy на российском сервере (aaPanel + Nginx)

### 6.1. Сайт и TLS

В aaPanel создай сайт `api.artem4ik493.ru`, выпусти TLS-сертификат и включи HTTPS. DNS должен указывать на российский сервер.

### 6.2. Пример Nginx

В upstream укажи внутренний адрес немецкого сервера, доступный через защищённый канал. `GERMANY_PRIVATE_IP` — placeholder, его нужно заменить реальным адресом.

```nginx
location / {
    proxy_pass http://GERMANY_PRIVATE_IP:3000;
    proxy_http_version 1.1;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 10s;
    proxy_read_timeout 60s;
    proxy_send_timeout 60s;
}
```

Этот пример подходит только если upstream использует HTTP внутри защищённого туннеля. При TLS на upstream настрой HTTPS и проверку сертификата. Не отключай проверку сертификата без обоснованной необходимости. Заголовки WebSocket добавляй, только если они требуются приложению.

Проверь конфигурацию через aaPanel или:

```bash
nginx -t
curl -I https://api.artem4ik493.ru/
```

Перезагружай Nginx только после успешной проверки синтаксиса. Убедись, что домен ведёт именно в Modexa, а не на дефолтную страницу.

## 7. Discord OAuth

В Discord Developer Portal проверь redirect URI:

```text
https://api.artem4ik493.ru/auth/discord/callback
```

Он должен посимвольно совпадать с `DISCORD_REDIRECT_URI` в немецком `.env`. OAuth client ID и secret храни только на сервере. После настройки проверь полный цикл входа через публичный домен: начало OAuth, callback и завершение сессии.

Приложение должно корректно обрабатывать `X-Forwarded-Proto` и доверять только ожидаемому reverse proxy. Не включай доверие к произвольным прокси.

## 8. Проверка ботов и Dashboard

После запуска в Германии проверь:

1. В логах нет ошибок конфигурации и авторизации.
2. Telegram-бот отвечает на `/help` и `/ping`, если команды есть в текущей версии.
3. Discord-бот онлайн, slash-команды зарегистрированы и работают.
4. Dashboard доступен по `https://api.artem4ik493.ru/`.
5. Текущие сценарии привязки Telegram/Discord работают.
6. SQLite-данные сохраняются после пересоздания/перезапуска контейнера.
7. Marzban и Marzban Node продолжают работать без изменений.

Команды диагностики:

```bash
docker ps --format 'table {{.Names}}\\t{{.Status}}'
docker logs --tail=200 <имя-контейнера-modexa>
docker logs -f <имя-контейнера-modexa>
```

Для выхода из просмотра логов нажми Ctrl+C — это не останавливает контейнер.

## 11. Безопасность

- Не коммить `.env`, токены, API-ключи, OAuth-секреты и базу данных.
- Не используй рабочие секреты-заглушки.
- Не открывай API всему интернету.
- Используй HTTPS снаружи и VPN-туннель либо TLS для upstream.
- Не меняй сетевой режим, порты, Compose-файлы и firewall Marzban.
- Не очищай `iptables`/ `nftables` и не заменяй firewall целиком.
- Ограничь права на секреты и базу.
- Настрой регулярное резервное копирование SQLite и проверь восстановление.
- После обновлений проверяй логи и состояние контейнера.
